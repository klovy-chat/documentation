Desktop does not have a second interface. Tauri opens the same frontend as the browser, just in a native window, with a badge and updater. A channel here is one group with one owner, not a server with roles — that is in [product](/docs/product), because you will not see it from `/api/channel` alone.

Traffic from the browser in production goes through Cloudflare Workers (SPA), then to the machine running the API. WebSocket does not ride "next to" REST on a different host — same origin `api.klovy.chat`, just an upgrade on `/ws`.

```
Przeglądarka / Tauri          Cloudflare              Backend
┌─────────────────┐           ┌──────────┐            ┌──────────────────────┐
│ app.klovy.chat  │  HTTPS    │ Workers  │  proxy     │ Axum (edge: CORS,    │
│ React + Vite    │──────────►│ (SPA)    │───────────►│ limity, proxy)       │
│                 │  WSS      └──────────┘            │        ▼             │
│ LiveKit client  │                                   │ Actix-web REST + WS  │
└────────┬────────┘                                   └─────────┬────────────┘
         │                                                      │
         │  media                                                ├─ MongoDB Atlas
         ▼                                                      ├─ R2 + ClamAV
   LiveKit Cloud                                                └─ LiveKit API
```

## What lives where

Frontend holds routes (login, signup, setup, pending, chat, invite, settings), auth / WebSocket / connection state, and strings in `pl.json` / `en.json`. In DEV, Vite proxies `/api`, `/whitelist`, and `/ws` to `127.0.0.1:8080`, so you do not have to glue CORS onto `localhost:5173` by hand — as long as the backend has `ORIGIN` and `FRONTEND_URL` set to that origin.

On the server, public traffic hits **Axum** first. That is CORS, rate limits, sometimes proxy. REST and WebSocket upgrade are handled by **Actix-web** on an internal port. Mongo holds users, channels, messages, sessions, and refresh tokens. A chat file does not land on a public CDN immediately: it goes to quarantine on R2, ClamAV scans it, and only when it is clean does the client get a URL.

Voice does not pass through our HTTP server. The backend signs a LiveKit token (`LIVEKIT_API_KEY` / `SECRET`) and returns `url` + `room`. Audio/video packets never hit Actix. The client still checks the host against `VITE_LIVEKIT_ALLOWED_HOSTS` (for us usually `*.livekit.cloud`). If someone slips a different URL into the token, the UI will not accept it.

## HTTP prefixes

The router often has two paths for the same thing: `/api/channel` and `/api/channels`, `/api/message` and `/api/messages`. That is not two controllers, just aliases, because old and new clients called them differently. Canonical paths used by the current frontend are in [API](/docs/api).

After login the order is always the same: cookies are already set, `GET /api` for limits and flags, `POST /api/auth/ws-crypto` for the key, then `/ws`. A frame is plain `{ type, payload }`. `type` names must match on both sides — the list is on the [WebSocket](/docs/api/websocket) page. Open the socket before `ws-crypto` and on production the client sends nothing; locally plaintext sometimes still works and then you wonder why prod "does not work".
