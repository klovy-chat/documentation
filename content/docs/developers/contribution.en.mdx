Code is under the **Klovy License**. We take issues and pull requests — an i18n typo counts, you do not have to rewrite half the backend. A small PR with one string lands faster than "also cleaned up three directories while I was here".

Before you open a PR, check you are editing the right repo. Frontend, backend, desktop, and product site are separate trees. Easy to put an API change in frontend "because client.ts is there", while the route still has to land in Rust. Docs changes go here, not in the frontend README, unless it is setup for that one repo.

1. Fork the repo your change belongs to.
2. Branch `feature/…` or `fix/…`. Name should say what it is, not `update` or `asdf`.
3. Commits must not include `.env`, keys, Mongo dumps, or `target/` / `node_modules` files.
4. PR targets `main`. In the description say what changed and why — two sentences is enough, no essay. If you touch an endpoint, note the path and whether the frontend already calls it.

Opening a PR, filing a bug, or an audit means you agree to license sections 7–11. That is not fine print in the footer; it is a condition of using the code.
