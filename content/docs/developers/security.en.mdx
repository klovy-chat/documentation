This is how it is built and where to report issues. No exploits, payloads, or "how to bypass this locally".

We do not keep session in `localStorage`, precisely so XSS cannot pull JWT with one script. Cookies are HttpOnly, browser mutations require CSRF (cookie `csrf_token` and the same string in `x-csrf-token`), Origin is checked. Login is rate-limited, Turnstile on production, optional TOTP. Chat files do not go straight to CDN: quarantine on R2, ClamAV, then public URL. Requests without `X-Klovy-Client` or from an origin off the list die at the edge. LiveKit token may return a `url` — the client still compares the host to `VITE_LIVEKIT_ALLOWED_HOSTS`.

Access and refresh are a cookie pair. On 401 the app calls `POST /api/auth/refresh` (no CSRF) and retries the original request. `GET /api/auth/sessions` lists devices. `DELETE` one session or `revoke-others` closes WebSocket with frame `session:revoked` — UI should log out, not hang on a dead socket.

New accounts may be on the whitelist. Screen `/pending` does not open WS. Backend would cut the handshake anyway, but there is no point doing a reconnect loop in the background.

Passwords: Argon2. Some Mongo fields are encrypted with a server key (that is not E2EE). WS frames after `POST /api/auth/ws-crypto` use AES-GCM. We do **not** call message content end-to-end: the server reads it for search, pins, and moderation. If a PR or README says "end-to-end encrypted", that is a mistake, not a feature.

Report vulnerabilities privately, in the repo that owns the code:

- [backend](https://github.com/klovy-chat/backend/security/advisories/new)
- [frontend](https://github.com/klovy-chat/frontend/security/advisories/new)
- [application](https://github.com/klovy-chat/application/security/advisories/new)

We close public issues with exploits. Do not commit `.env`, `TAURI_SIGNING_PRIVATE_KEY`, or database dumps.
